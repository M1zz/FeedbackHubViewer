# FeedbackHub Viewer (macOS · iOS · iPadOS)

`iCloud.com.Ysoup.FeedbackHub` 컨테이너의 **Public 데이터베이스**에 쌓인 사용자 피드백을
한눈에 볼 수 있는 SwiftUI 앱입니다. 하나의 타겟이 macOS와 iPhone/iPad에서 모두 돌아갑니다.
목록·상세 보기, 검색·필터·정렬, 통계 대시보드, 진단 모아보기, 수동/자동 새로고침을 지원합니다.

화면 위계는 **프로젝트 우선**입니다. 먼저 프로젝트를 고르고, 그 안에서 **피드백 · 통계 · 진단**을
상단 세그먼트로 전환합니다.

- **Mac / iPad**: 프로젝트 목록(사이드바) + 그 프로젝트의 피드백·통계·진단 + 피드백 상세의 3열
- **iPhone**: 프로젝트 카드 목록 → 프로젝트 화면(피드백·통계·진단) → 피드백 상세의 단일 스택
  (탭 바 없음)

> ⚠️ 이 zip에는 **완성된 `.app` 실행 파일이 아니라 Xcode 프로젝트 소스**가 들어 있습니다.
> CloudKit 접근에는 본인의 Apple 개발자 계정 서명이 반드시 필요하기 때문에,
> 여러분이 Xcode에서 직접 빌드해야 정상 동작합니다. (아래 절차 참고)

---

## 1. 필요 환경

- macOS 14 (Sonoma) 이상 / iOS·iPadOS 17 이상
- Xcode 16 이상
- `com.Ysoup.FeedbackHub` 앱이 속한 **Apple Developer 팀 계정** (CloudKit 컨테이너 접근 권한이 있어야 함)

## 2. 빌드 & 실행 절차

1. 압축을 풀고 `FeedbackHubViewer/FeedbackHubViewer.xcodeproj`를 Xcode로 엽니다.
2. 프로젝트 네비게이터에서 **FeedbackHubViewer 타겟 → Signing & Capabilities** 탭으로 이동합니다.
3. **Team**을 여러분의 개발자 팀(FeedbackHub 컨테이너에 접근 권한이 있는 팀)으로 선택합니다.
4. **iCloud** Capability에 `iCloud.com.Ysoup.FeedbackHub` 컨테이너가 체크되어 있는지 확인합니다.
   (이미 entitlements에 지정돼 있지만, 팀을 바꾸면 Xcode가 목록을 다시 불러옵니다.)
5. 필요하다면 **Bundle Identifier**(`com.Ysoup.FeedbackHubViewer`)를 여러분 것에 맞게 바꿔도 됩니다.
   단, iCloud 컨테이너 ID(`iCloud.com.Ysoup.FeedbackHub`)는 **그대로 두어야** 같은 데이터를 봅니다.
6. 실행 대상(destination)에서 **My Mac** 또는 **iPhone/iPad(시뮬레이터·실기기)** 를 고르고 `⌘R`로 실행합니다.
   기기에 iCloud 로그인이 되어 있어야 합니다(Security Role은 로그인한 계정 기준으로 판정됩니다).

## 2-1. Production 데이터 읽기

CloudKit은 어느 환경을 읽을지 **빌드에 박히는 entitlement**
(`com.apple.developer.icloud-container-environment`)로 정합니다. 런타임 토글은 불가능하므로,
**스킴을 골라서** 환경을 바꿉니다. Xcode 스킴 선택기에서 고르고 `⌘R`만 하면 됩니다.

| 스킴 | 빌드 구성 | 읽는 환경 | 번들 ID |
| --- | --- | --- | --- |
| `FeedbackHubViewer` | Debug | Development | `com.Ysoup.FeedbackHubViewer` |
| `FeedbackHubViewer (Production)` | Debug-Production | Production | `com.Ysoup.FeedbackHubViewer.prod` |
| (Archive/Release) | Release | Production | `com.Ysoup.FeedbackHubViewer` |

번들 ID가 달라서 **두 앱을 한 기기에 동시에 설치**해 놓고 오가며 볼 수 있고,
앱 아이콘도 다릅니다(Development=파랑, Production=초록).
현재 보고 있는 환경은 화면의 `DEV`/`PROD` 배지와 툴바 "내 계정 ID" 메뉴에서 확인할 수 있습니다.

> **Production에서 데이터가 보이려면 Console 작업이 선행되어야 합니다.**
> [CloudKit Console](https://icloud.developer.apple.com/dashboard/)에서 스키마와
> Security Role(admin 역할에 내 userRecordName 등록 + 피드백 레코드 타입 read 권한)을
> **Deploy to Production** 해야 합니다. 배포 전에는 `permissionFailure`가 납니다.
> 등록에 쓸 내 userRecordName은 권한 오류 메시지와 툴바 "내 계정 ID" 메뉴에 표시됩니다.

## 2-2. 기기 사이에서 같은 숫자 보기 (iCloud 요약본)

**실행하면 iCloud에 있는 마지막 요약본을 먼저 받아오고, 새로고침하면 그 요약본이 갱신됩니다.**
맥에서 "7일 활성 120명"인데 아이폰에서 80명으로 뜨던 문제가 이것으로 없어집니다.

왜 달랐냐면, 지금까지는 기기마다 **자기가 읽어 낸 것만** 가지고 자기 화면을 만들었기 때문입니다.
`UsageEvent`는 최신부터 읽다가 이미 가진 레코드를 만나면 멈추므로 한 번 생긴 구멍은 그 기기에 남고,
날짜 버킷은 그 기기가 읽은 이벤트만큼만 쌓이며, 원본 이벤트는 90일·진단은 1,000건까지만 남깁니다.
언제부터 그 기기를 썼느냐가 곧 숫자가 됐던 셈입니다.

- **어디에 두나**: 이 iCloud 계정의 **비공개(private) 데이터베이스**, 컨테이너는 허브와 같은
  `iCloud.com.Ysoup.FeedbackHub`. 레코드 타입 `HubSummary` 하나, 레코드 하나, 첨부 파일 하나입니다.
  공개 DB는 앱들이 쓰는 곳이고 뷰어에는 읽기 권한밖에 없어서 여기에 둘 수 없고,
  읽음·처리를 나누는 키·값 저장소(1MB 한도)에 넣기에는 요약본이 큽니다.
- **무엇이 담기나**: 새로고침이 만들어 낸 결과 전체 — 레코드 캐시와 날짜 버킷, 즉 앱이 디스크에 쓰는
  바로 그것입니다. zlib으로 줄여서 올립니다(스냅샷 6,300건 기준 8MB → 600KB, 전체 2MB 남짓).
- **합치는 규칙**: 받은 것으로 갈아끼우지 않고 **합칩니다**. 레코드는 이름으로, 날짜 버킷은 칸마다
  더 완전한 쪽(활동 설치는 합집합, 건수는 큰 쪽)을 취합니다. 그래서 어느 기기가 언제 올리든
  모두가 같은 값으로 수렴합니다.
- **언제 올리나**: 손으로 누른 새로고침(`⌘R`·당겨서 새로고침)은 그때마다, 1분짜리 자동 갱신은
  10분에 한 번. 올릴 것이 없으면 올리지 않습니다.
- **예외**: "캐시 비우고 전체 다시 불러오기"는 합치지 않고 **덮어씁니다**. 이 기기 기준으로 처음부터
  다시 만들겠다는 뜻이므로, 합치면 방금 버린 것이 저쪽에서 그대로 돌아옵니다.
- 지금 상태(언제·어느 기기가 만든 요약본인지)는 툴바 "내 계정 ID" 메뉴의 **기기 사이 숫자**에 나옵니다.

> **Production에서는 스키마를 한 번 배포해야 합니다.**
> CloudKit의 레코드 타입은 컨테이너 단위라, 비공개 DB에 쓰는 것이라도 Production 스키마에 있어야
> 합니다. Development 스킴으로 한 번 실행해서 새로고침하면 `HubSummary` 타입이 자동으로 만들어지고,
> [CloudKit Console](https://icloud.developer.apple.com/dashboard/) → 컨테이너 → Schema →
> **Deploy Schema Changes**로 Production에 올리면 됩니다. 배포 전에는 요약본만 못 오가고
> (메뉴에 안내 문구가 뜹니다) 나머지는 지금까지처럼 동작합니다.
>
> 키워드 순위 기록은 아직 여기 포함되지 않습니다 — App Store를 읽는 별개의 저장소라
> 기기마다 확인한 날짜가 다를 수 있습니다.


## 3. 주요 기능

- **목록 + 상세**: Mac/iPad는 오른쪽 열, iPhone은 화면 전환으로 전체 내용과 모든 필드를 봅니다.
  (iPhone 상세 화면에는 텍스트 전체를 복사·공유할 수 있는 공유 버튼이 있습니다.)
- **검색**: 목록 위 돋보기 버튼(macOS는 툴바 검색)으로 열어 본문·버전·기기·이메일·기타 모든 필드를
  키워드로 찾습니다. 평소에는 자리를 차지하지 않습니다.
- **필터·정렬**: 피드백 목록 위 "정렬 · 필터" 메뉴에서 정렬(최신순 / 오래된순 / 별점 높은순 /
  별점 낮은순)과 앱 버전·최소 별점 필터를 겁니다. 프로젝트 선택은 한 단계 위(사이드바 / 프로젝트 목록).
- **정렬**: 프로젝트 목록·사이드바는 **트래픽이 많은 순**입니다 — 최근 7일 사용 건수(UsageEvent) →
  최근 7일 활동 사용자 → 설치 수 → 피드백 수 → 이름 순으로 비교하고, `미분류`는 맨 아래입니다.
  그 기준이 되는 숫자를 카드와 사이드바에 함께 적고("최근 7일 사용 N건 · 활성 M명 · 설치 K대"),
  최근 14일 사용량 스파크라인을 카드·사이드바 양쪽에 나란히 그립니다.
- **프로젝트 선택**: 허브에 무엇이든 올린 앱은 모두 나옵니다 — 피드백이 아직 없고 사용 통계나 진단만
  보낸 앱도 목록에 있고, 피드백 0건으로 표시됩니다.
  카드마다 숫자 밑에 이름이 붙습니다 — 피드백 / 안 읽음 / 평균 별점 / 최근 7일,
  그리고 최근 7일 진단이 있으면 빨간 줄로 함께. 고르면 그 프로젝트의 피드백·통계·진단으로 들어가고,
  화면 위의 큰 세 버튼(피드백 · 통계 · 진단)으로 전환합니다.
- **안 읽음 배지**: 상세를 연 피드백만 읽음으로 기록하고(기기별 `UserDefaults` 저장), 안 읽은 건수를
  앱 아이콘 배지·프로젝트 카드/행·목록 행의 점으로 표시합니다. 피드백 목록 위 "모두 읽음"으로 한 번에
  지울 수 있습니다.
- **처리(반영/반영 안 함)**: 피드백마다 **반영함 / 반영 안 함**을 표시하고 메모("v1.4에 반영",
  "중복 피드백")를 남깁니다. 목록 각 줄 오른쪽의 **반영함** 동그라미, 행 스와이프(왼쪽=반영함,
  오른쪽=반영 안 함), 행 우클릭 메뉴, 상세 화면의 "처리" 칸 어디서든 지정할 수 있고,
  macOS·iOS 모두 동일하게 동작합니다.
  - 목록은 기본적으로 **확인 필요만** 보여줍니다. 처리한 피드백은 목록에서 바로 빠지고,
    목록 맨 아래 **"처리한 피드백 N건 보기"**로 다시 볼 수 있습니다("정렬 · 필터" 메뉴의
    처리 상태에서 확인 필요 / 처리 완료 / 반영함 / 반영 안 함 / 전체를 직접 고를 수도 있습니다).
  - 남은 건수는 목록 위 바(주황 배지)·프로젝트 화면 부제·프로젝트 카드에 나옵니다.
    같은 메뉴의 **표시된 N건 모두 …**로 한 번에 처리할 수도 있습니다(확인 후 적용).
  - 표시와 메모는 **이 기기에만**(`UserDefaults`) 저장됩니다. 이 뷰어는 허브를 읽기만 하므로
    **CloudKit 레코드는 전혀 바뀌지 않습니다** — 다른 기기와 공유되지 않습니다.
  - 상세를 여는 것만으로는 처리되지 않습니다 — 읽음과 처리는 별개입니다.
- **통계**: 각 앱이 허브로 보내는 **사용 통계(UsageSnapshot / UsageEvent)를 그대로** 보여줍니다.
  프로젝트 화면의 **통계** 세그먼트가 그 프로젝트의 대시보드입니다(전체 프로젝트를 고르면 합계).
  대시보드에는 사용자 타일, 지난주 대비, **성장 상한**, 기간별 추이(일·주·월·연),
  사용 내역(이벤트 하나하나), 이벤트별 건수/설치 수, 설치당 평균 지표, 플래그 비율,
  버전·플랫폼·OS 분포, 피드백 요약이 들어갑니다.
  **성장 상한(carrying capacity)**: 지금의 유입과 지금의 이탈이 이어질 때 활동 사용자가 멈추는
  자리를 `기간당 신규 ÷ 기간 이탈률`로 계산해 보여줍니다(주간·월간 전환). 상한과 지금 자리를
  막대 하나로 겹쳐 놓고, 그 상한을 만든 두 숫자(신규·이탈률)와 평균 사용 수명을 같이 적고,
  실제 궤적 위에 전망선과 상한선을 얹습니다. 계산 근거와 한계는 아래 §5-3.
  **크래시·진단은 통계에 없습니다** — 옆의 진단 세그먼트가 그 화면입니다(최근 7일 진단이 있는 앱에는
  프로젝트 목록·사이드바에 빨간 ⚠︎가 붙습니다).
  **앱별 지표**: 각 앱은 자기 화면에서 쓰는 어휘(metrics 키·이벤트 이름)와 해석(무료 한도 같은
  경계)이 다릅니다. 그 규칙을 앱 리포의 `docs/usage-spec.json`에 두고
  `scripts/sync-stats-specs.sh`로 `FeedbackHubViewer/Specs/`에 가져옵니다 — 뷰어는 그대로 그리므로
  ClipKeyboard는 "키보드 사용량·단축어 개수 분포·사용 유형"이, 두번알림은 "결제 준비도·완주 분포·
  알림 개수 수요·사용자 구분"이 앱에서 보던 그대로 나옵니다. 스펙에 없는 키는 감추지 않고 원문
  그대로 보여주며, 화면 아래 **스펙에 없는 지표** 카드로 알려 줍니다(앱이 새 지표를 추가한 신호).
  스펙 없는 앱은 지금까지처럼 일반 화면입니다.
  **결제 퍼널**(`funnels`)은 스펙에서 유일하게 스냅샷이 아니라 **이벤트**를 읽습니다 — 결제는
  설치에 남는 상태가 아니라 일어난 일이니까요. 단계는 이벤트 기본형으로 적고, 슬라이스
  (`paywall_cta_tapped:buy` · `:memo`)는 한 단계로 합칩니다. 기본은 **설치 수**(`basis`)입니다:
  한 사람이 페이월을 열 번 봐도 한 명이고, 슬라이스별 집합은 합집합이라 둘 다 누른 사람이 둘로
  세어지지 않습니다. 값은 전 기간 집계(§5-2)에서 바로 나오므로 원본 이벤트를 훑지 않습니다.
  퍼널이 정직하려면 각 칸이 앞 칸에 **포함**돼야 하는데 이벤트 이름만으로는 그걸 강제할 수 없어서,
  화면이 두 가지를 그대로 드러냅니다:
    - **보내지 않음**(회색): 그 이벤트가 한 번도 도착한 적 없음. 아무도 거기까지 못 간 게 아니라
      앱이 안 보내는 것이므로 스펙이 아니라 앱을 고쳐야 합니다.
    - **앞 단계 밖에서도 옴**(주황): 앞 칸보다 수가 많음. 그 자리는 다른 경로로도 닿는다는 뜻이라
      전환율인 척하지 않습니다. 경로를 나누려면 앱이 이벤트에 출처 슬라이스를 붙여 보내야 합니다.
  **사용 내역** 카드는 "최근 7일 사용 N건"의 그 N건을 실제로 보여줍니다 — 이벤트 이름, 발생 시각,
  설치 ID 앞 8자리, 버전·플랫폼이 한 줄씩. 20건부터 "더 보기"로 50건씩 늘립니다.
  이벤트 이름과 `metrics` 키는 앱이 보낸 원문 그대로 표시합니다(뷰어가 앱별 용어를 번역하지 않습니다).
- **진단**: 프로젝트 화면의 **진단** 세그먼트(또는 안정성 카드의 "전부 모아보기").
  툴바에서 두 시야를 오갑니다.

  - **이슈** (기본): 같은 사고끼리 묶어 **아픈 것부터** 보여 줍니다. 한 줄에 범인 프레임,
    원인(워치독 종료 지연 · 화면 갱신 지연 · 신호 · 멈춤 · 메모리), 건수, 최근 7일과 지난주 대비,
    영향 버전·기기 종류, 그리고 **새로 생김** / **최근 7일 없음** 표시가 붙습니다.
    맨 위에는 아직 나는 이슈 수 · 최근 7일 건수 · 새로 생긴 이슈 수가 섭니다.
    이슈를 누르면 첫 등장과 마지막, 버전·기기·OS 분포, **내 코드 프레임을 굵게 그린 콜스택**,
    개별 진단 목록, 그리고 "무엇을 보면 되는지" 한 줄 안내가 나옵니다.
  - **전체**: 예전처럼 한 건씩, **앱 버전별로 묶어서**(최신 버전이 위, 묶음 안에서는 최신순).
    종류 필터, 프로젝트별 건수, 콜스택 펼치기, 개별/전체 복사.

  왜 묶는 쪽이 기본인가: 한 건씩 늘어놓은 목록으로는 "무엇을 먼저 고칠까"를 고를 수 없습니다.
  묶는 규칙과 그 한계는 `CrashAnalysis.swift` 머리말에 적어 두었습니다.
- **키워드**: 프로젝트 화면의 **키워드** 세그먼트. App Store 검색에서 이 앱이 몇 위인지,
  누가 위에 있는지를 매일 추적합니다. 허브가 이미 아는 번들 ID로 App Store 앱을 **자동으로**
  이어 붙이므로(`lookup?bundleId=`) 앱을 따로 등록할 일이 없습니다.

  **검색어를 떠올리지 않아도 됩니다.** `앱 이름으로 자동 찾기`를 누르면 이 앱 이름으로 한 번
  검색해 같은 자리에 서는 앱들을 모으고, 그 이름들이 공통으로 쓰는 말을 후보로 뽑은 다음,
  하나씩 실제로 검색해서 **순위에 잡히는 것만** 남깁니다 (클립키보드의 경우 아무것도 입력하지
  않고 클립키보드 1위 · 클립보드 18위 · 붙여 45위 · 넣기 69위 · clipboard 70위 · 복사 128위를
  찾았고, 안 잡힌 키보드·keyboard·paste·클립은 버렸습니다). 후보를 뽑는 규칙은 형태소 분석기가
  없는 어림이라 가끔 "붙여" 같은 조각이 섞입니다 — 판정은 어디까지나 실제 검색이 하고,
  어색한 줄은 우클릭 → 추적 중단으로 지웁니다. 검색어 하나당 3초라 열두 개면 30초쯤 걸립니다.

  검색어를 직접 넣고 국가를 고르면 그 자리에서 한 번 확인하고, 그 뒤로는 **하루에 한 번** 확인합니다
  (순위는 하루 단위로 움직이므로 실행할 때마다 물어볼 이유가 없습니다). 각 줄에는 순위,
  전날 대비 변화(순위는 내려가는 쪽이 좋으므로 **−6이 초록**), 30일 스파크라인이 서고,
  줄을 누르면 그 검색어의 상위 10개와 그 안의 내 앱 위치가 펼쳐집니다.
  목록은 **순위순**이고, 각 줄에 **"N개 앞섬"** 이 함께 섭니다 — 위에 있는 앱 중 내 앱보다
  리뷰가 *많은* 것의 수입니다. 18위인데 위 17개 중 7개가 나보다 작으면 실제로는 10개 뒤이고,
  21위인데 20개 중 13개가 작으면 7개 뒤라 순위가 낮아도 그쪽이 더 가깝습니다. 순위만으로는
  "17위인데 위가 전부 자리 잡은 앱"과 "17위인데 위가 전부 리뷰 0개"를 구별할 수 없습니다.
  리뷰 수는 얼마나 자리 잡았는지를 재는 거친 대용이지만 **측정값**입니다(검색량처럼 지어낸
  값이 아닙니다). 지어낸 수를 섞어 점수 하나로 만들지 않고 숫자를 그대로 둡니다.

  **경쟁 앱**은 추적 중인 검색어에서 실제로 마주친 앱을 내 위에 있는 횟수 순으로 세웁니다.
  줄을 누르면 그 앱의 App Store 페이지가 열립니다 —
  즉 **검색어가 없으면 경쟁 앱도 없습니다**. 순위도 경쟁 앱도 전부 검색어에서 나오므로,
  빈 화면에서는 그 사실과 자동 찾기 버튼을 함께 보여 줍니다.

  설계의 핵심은 **검색 한 번이 내 앱 전부를 커버한다**는 것입니다. "메모"를 앱 셋에서
  추적해도 요청은 1건이고, 그 결과에서 세 앱의 순위를 동시에 읽습니다 — 요청 비용이
  `검색어 × 국가`이지 `앱 × 검색어`가 아닙니다. 앱이 스무 개 넘을 때 결정적입니다.

  **이 화면이 보여주지 않는 것**(화면 안에도 적어 두었습니다): 검색량은 없습니다 —
  애플이 공개하지 않고, 다른 ASO 툴의 검색량도 전부 추정 모델입니다. 순위는 iTunes Search API의
  결과 순서로, 앱 안의 검색 순위에 아주 가깝지만 같다는 보장은 없습니다. Google Play는
  공식 API가 없어 지원하지 않습니다.

  순위 이력은 `keywords.json`에 남고, **실행하면 허브를 기다리지 않고 바로 그려집니다** —
  이 파일은 그 자체로 완결이라 8 MB짜리 허브 캐시가 풀리기를 기다릴 이유가 없습니다
  (Production 기준 키워드 화면 53 ms · 허브 복원 340 ms). 네트워크로 다시 확인하는 쪽만
  허브의 앱 목록을 기다립니다. 이 파일만은 CloudKit 환경으로 나뉘지 않습니다 — App Store는
  어느 컨테이너를 읽든 같은 App Store입니다.

  파일은 읽는 것만 남깁니다. 검색 결과 상위 30개는 **각 검색어의 가장 최근 확인**에만 두고
  (경쟁 앱과 펼친 줄은 지금의 스토어를 묻지 작년 순위를 묻지 않습니다), 지난 날은 순위만
  남기며, 400일이 지나면 그 날도 버립니다. 어떤 결과에서도 사라진 앱은 이름표를 붙일 데가
  없으므로 함께 지웁니다. 앱 설명은 아예 저장하지 않습니다 — 읽는 곳이 없었습니다.
  이 정리로 467 KB가 76 KB가 됐습니다.
- **앱 아이콘**: 사이드바(와 iPhone 프로젝트 카드)의 빈 네모 자리에 실제 App Store 아이콘이
  들어갑니다. 앱이 스무 개 넘으면 이름 스무 개를 읽는 것보다 아이콘으로 알아보는 게 훨씬 빠릅니다.
  키워드 기능이 실행할 때 번들 ID로 앱을 이어 붙이므로(`KeywordStore`) 추가 요청이 들지 않고,
  이미지는 `URLSession` 공용 캐시가 실행 사이에 들고 있습니다. 스토어에 없는 앱(개발용 빌드,
  심사 중)은 원래의 점선 네모로 남습니다 — 못 불러온 아이콘처럼 보이면 안 되니까요.
- **프로젝트 숨기기**: 사이드바 프로젝트 행(오른쪽 클릭 또는 스와이프)이나 프로젝트 카드 우클릭에서
  "이 프로젝트 숨기기". 그 앱의 피드백·사용 통계·이벤트·크래시가 목록과 집계에서 한꺼번에
  빠집니다. **허브의 레코드는 지우지 않습니다** — 이 기기의 표시 설정(`UserDefaults`)일 뿐이고,
  사이드바(또는 프로젝트 목록) 아래 "숨긴 프로젝트"에서 언제든 되돌립니다.
- **알림 · 배지**: 툴바의 종 버튼(iPhone은 "더 보기" 메뉴)의 **새 피드백·진단 알림** 토글을 켜면, 새로고침에서
  전에 못 보던 레코드를 발견할 때 알림을 보내고 앱 아이콘 배지에 안 읽은 피드백 수를 표시합니다.
  처음 켤 때 시스템 알림 권한을 요청하고, 거부돼 있으면 토글 아래에 안내가 뜹니다.
  - 첫 실행에는 이미 쌓여 있던 레코드로 알림이 오지 않도록 조용히 기준선만 저장합니다(기기별).
  - **앱이 떠 있는 동안** 동작합니다("자동 갱신"을 켜두면 1분마다 확인). 앱이 꺼진 상태에서도 받으려면
    Push Notifications capability + `CKQuerySubscription`이 필요합니다(미구현).
  - macOS는 알림 권한이 없으면 Dock 배지도 표시되지 않습니다(시스템 정책).
- **즉시 실행(로컬 캐시)**: 마지막으로 성공한 조회 결과를 기기에 저장해 두고, 다음 실행에서는 **먼저 그
  화면을 그린 뒤** CloudKit에 "바뀐 게 있는지"를 백그라운드로 확인합니다. 실행할 때마다 로딩을 기다리지
  않아도 되고, 확인이 끝나면 화면이 조용히 갱신됩니다(툴바에 "업데이트 확인 중…" 표시).
  - 저장 위치는 앱 컨테이너의 `Application Support/FeedbackHubViewer/` 아래 두 파일이며,
    **Development/Production 캐시가 분리**됩니다. CloudKit 레코드는 건드리지 않습니다.
      - `hub-<환경>.json` — 레코드 원본(피드백·스냅샷·진단, 그리고 최근 90일치 이벤트)
      - `rollups-<환경>.json` — 이벤트를 **일 단위로 합쳐 둔 것**(아래 §5-2)
  - **읽는 도중에도 계속 저장합니다.** 레코드 500건이 모일 때마다(그리고 레코드 타입 하나를 끝낼 때마다)
    지금까지 받은 것을 파일에 씁니다. 첫 실행은 스냅샷·이벤트 수천 건을 몇 분에 걸쳐 읽는데, 예전에는
    **네 종류를 전부 읽고 난 뒤에 딱 한 번** 저장했기 때문에 그 전에 앱을 끄거나(맥) 홈으로 나가면
    (iOS) 받은 것이 **전부 사라지고** 다음 실행에서 처음부터 다시 읽었습니다. 앱이 종료·백그라운드로
    갈 때도 아직 안 쓴 것을 그 자리에서 마저 씁니다(`FeedbackStore.flushCache()`).
    - 중간에 끊긴 레코드 타입에는 워터마크가 남지 않고, 다음 실행은 그 타입을 **처음부터 다시** 읽습니다.
      중간까지만 받아 둔 상태에서 "이미 가진 것에서 멈추기"를 쓰면 그 뒤쪽 과거가 영영 안 읽히기 때문입니다.
  - 백그라운드 확인은 **증분**입니다. 피드백·이벤트·진단은 추가만 되고 과거 레코드가 바뀌지 않으므로,
    최신순으로 읽다가 **이미 기기에 있는 레코드를 만나면 거기서 멈춥니다** — 스키마 설정과 무관하게
    "저장돼 있지 않은 것만" 내려받습니다(없으면 첫 페이지 한 번으로 끝). 스키마에서 시스템
    타임스탬프가 **Queryable**이면(아래 §5-7) 서버 쪽 날짜 필터까지 함께 걸어 더 줄입니다.
  - `UsageSnapshot`만 예외로 매번 전부 읽습니다. 설치마다 같은 레코드를 덮어쓰는 구조라 "이미 있는
    레코드명"이 곧 다시 읽어야 할 대상이기 때문입니다(설치 수만큼이라 양이 작습니다).
  - 콘솔에서 레코드를 **삭제**한 경우는 증분 조회로 알 수 없으므로, 캐시가 24시간이 지났거나 직접
    새로고침을 누르면 전체를 다시 읽어 교체합니다. "내 계정 ID" 메뉴의 **캐시 비우고 전체 다시 불러오기**로
    언제든 강제할 수 있습니다.
  - 단 `UsageEvent`만은 **전체 조회에서도 이미 가진 것에서 멈춥니다**. 이벤트는 이미 일 단위로 합산돼
    있어서 지운다고 그 날의 합계를 되돌릴 수 없고, 전체 재조회는 가장 비싼데 얻는 게 없기 때문입니다.
    합계까지 처음부터 다시 만들려면 **캐시 비우고 전체 다시 불러오기**를 쓰세요.
- **새로고침**: 툴바의 새로고침 버튼(macOS `⌘R`), iPhone에서는 당겨서 새로고침, "자동 갱신" 토글(1분 주기).
  새로고침 버튼은 항상 **전체 조회**이고, 앱 실행·자동 갱신은 증분 조회입니다.

## 4. 데이터 구조에 대한 참고 (중요)

정확한 CloudKit 스키마를 알려주지 않으셨기 때문에, 앱은 **일반적인 구조로 추정**해서 동작합니다.

- **레코드 타입**: `Feedback`, `Feedbacks`, `FeedbackItem`, `UserFeedback`, `Review` 등
  흔한 이름을 차례로 시도해 데이터가 나오는 첫 타입을 사용합니다.
  실제 타입 이름이 다르면 **`CloudKitService.swift`의 `candidateRecordTypes` 배열 맨 앞에
  실제 이름을 추가**하고 다시 빌드하세요.
- **필드 매핑**: 아래 이름들을 자동으로 인식합니다(대소문자 무시).
  - 본문: `text`, `message`, `content`, `body`, `feedback`, `comment`, `description` …
  - 별점: `rating`, `stars`, `score`, `rate`
  - 앱 버전: `appVersion`, `version`, `buildVersion` …
  - 기기: `deviceModel`, `device`, `model` …
  - OS: `systemVersion`, `osVersion`, `os` …
  - 이메일: `email`, `contactEmail`, `contact` …
  인식하지 못한 필드도 상세 화면의 **"모든 필드"** 표에 그대로 표시되므로 데이터는 절대 누락되지 않습니다.

### 4-1. 사용 통계 스키마 (추정 아님, 고정)

피드백과 달리 사용 통계는 LeeoKit(`LeeoUsageReporter`)이 쓰는 **고정 스키마**라 그대로 읽습니다.
같은 컨테이너의 Public DB이고, 앱 쪽 정책·주기는 각 앱의 `UsageReportingService`와
`docs/USAGE_STATS_HUB.md`에 있습니다.

| 레코드 타입 | 단위 | 필드 |
|---|---|---|
| `UsageSnapshot` | 설치 1건(레코드 이름 `usage-<installID>`, upsert) | `appId` `appName` `appVersion` `platform` `osVersion` `locale` `launchCount` `eventCount` `daysSinceInstall` `installDate` `lastActiveAt` `metrics`(JSON `[String: Double]`) |
| `UsageEvent` | 주요 행동 1건 | `appId` `appName` `event` `appVersion` `platform` `installID` `occurredAt` |
| `CrashReport` | MetricKit 진단 1건 | `appId` `kind`(crash/hang/disk_write) `detail` `appVersion` `osVersion` `deviceType` `stack` · **`occurredAt`**(Date) `buildNumber` `exceptionType` `exceptionCode` `signal` |

- 추이·활성 사용자는 **`occurredAt`** 으로 계산합니다. `creationDate`(서버가 쓴 시각)로 세면
  나중에 소급 전송된 활동일이 보낸 날 하루에 뭉칩니다.
- 활성/신규는 앱 화면과 같은 정의입니다: 최근 N일 활성 = `lastActiveAt`이 그 구간인 스냅샷,
  최근 N일 신규 = `installDate`가 그 구간인 스냅샷, 활동한 사용자 = 구간 내 서로 다른 `installID`.
- `metrics` 키와 이벤트 이름은 앱마다 다릅니다. 뷰어는 키를 해석하지 않고 그대로 나열하며,
  `flag.*` · `persona.*` 키만 0/1 플래그로 보고 "사용자 비율"에 넣습니다.
- `CrashReport`의 뒤쪽 5개 필드는 **ClipKeyboard 5.0.6부터** 옵니다. 그 이전 레코드에는 없으므로
  뷰어는 전부 없을 수 있다고 보고 다룹니다. `occurredAt`이 없으면 **레코드 생성 시각**으로 대신하고,
  이슈 상세에 그 사실을 표시합니다(MetricKit 배달이 하루까지 늦으므로 실제 발생은 그보다 앞섭니다).
- ⚠️ `appVersion`은 **배달 시점에 깔려 있던** 버전입니다. 죽은 버전이 아닐 수 있습니다.
  정확한 값은 `buildNumber`(`MXMetaData.applicationBuildVersion`)이고, 둘이 어긋나면 이름표를 의심합니다.
- ⚠️ `stack` 형식이 5.0.6에 바뀌었습니다. 그 전에는 잘린 JSON 덩어리라 **갈라 볼 수 없습니다**.
  뷰어는 `{`로 시작하는지로 구분해 옛 레코드를 "옛 형식" 한 덩어리로 모으고 이유를 화면에 적습니다.
  왜 그렇게 됐는지는 ClipKeyboard 저장소의 `docs/postmortem/CRASH_STACK_TRUNCATION.md`.
- 한 번에 읽는 양은 이벤트 5,000건, 진단 1,000건이 상한입니다
  (`CloudKitService.fetchUsage(eventLimit:crashLimit:)`). 이벤트는 이 상한이 **화면의 숫자에 영향을
  주지 않습니다** — 도착할 때 일 단위로 합산해 두기 때문입니다(§5-2).
- 이벤트 기준 "최근 7일"은 **오늘 포함 7일(하루 단위)**입니다. 설치 기준(`active7`·`new7`)은 스냅샷의
  타임스탬프를 그대로 보므로 여전히 "지금부터 168시간"입니다.
- 사용 통계를 못 읽어도 피드백은 정상 동작하고, 통계 화면 위에 사유가 배너로 뜹니다.

## 5. 데이터가 안 보일 때 체크리스트

CloudKit Public DB는 필드가 **Queryable**로 표시돼 있어야 조회되고, 정렬하려면 **Sortable**이어야 합니다.
비어 있게 나온다면 [CloudKit Console](https://icloud.developer.apple.com/dashboard/)에서 다음을 확인하세요.

1. 컨테이너 `iCloud.com.Ysoup.FeedbackHub` → **Schema → Record Types**에서 피드백 레코드 타입의 실제 이름 확인
   (다르면 `candidateRecordTypes`에 추가).
2. 조회에 쓰는 시스템 인덱스 `recordName`(및 필요한 필드)이 **Queryable**로 설정돼 있는지 확인.
3. 정렬용으로 `createdTimestamp`가 **Sortable**인지 확인. (아니어도 앱은 자동으로 정렬 없이 다시 조회합니다.)
4. **Environment**: 개발 중에는 Development, 배포된 데이터는 Production에 있습니다.
   `FeedbackHubViewer` 스킴은 Development, `FeedbackHubViewer (Production)` 스킴은 Production을 봅니다(위 2-1 참고).
5. **권한**: LeeoKit은 World에서 read를 빼고 저장하므로, CloudKit Console → Security Roles의 admin 역할에
   내 iCloud **userRecordName**을 등록하고 피드백 레코드 타입에 read를 줘야 합니다.
   권한 오류가 나면 앱이 등록에 쓸 userRecordName을 오류 메시지와 "내 계정 ID" 메뉴에 표시합니다.
6. **사용 통계·진단**: `UsageSnapshot` · `UsageEvent` · `CrashReport`도 같은 admin 역할에 read가
   필요하고, 해당 환경에 스키마가 배포돼 있어야 합니다(`UsageSnapshot`은 `recordName` Queryable,
   `UsageEvent`·`CrashReport`는 `recordName` Queryable + `createdTimestamp` Sortable).
   없으면 통계 화면 상단에 어떤 레코드 타입이 왜 안 읽혔는지 표시됩니다.
7. **증분 조회(선택)**: 앱 실행·자동 갱신은 "마지막 조회 이후 바뀐 것만" 읽으려고 시도합니다. 이건
   각 레코드 타입의 시스템 타임스탬프가 **Queryable**일 때만 됩니다 — Schema → Record Types →
   해당 타입 → Indexes에서 `createdTimestamp`(추가·삭제만 있는 `Feedback` · `UsageEvent` ·
   `CrashReport`)와 `modifiedTimestamp`(설치마다 덮어쓰는 `UsageSnapshot`)를 **QUERYABLE**로 추가하세요.
   지금 컨테이너는 둘 다 안 돼 있습니다. 안 돼 있어도 "이미 가진 레코드를 만나면 멈추는" 방식이
   따로 동작하므로 새 레코드만 내려받는 건 그대로이고, 설정해 두면 서버 쪽에서 한 번 더 걸러
   페이지 하나조차 안 받게 됩니다. 앱이 한 번 시도해 보고 알아서 넘어가므로 코드 변경은 없습니다.

## 5-1. 화면의 숫자는 새로고침마다 한 번만 계산합니다

프로젝트 카드·사이드바·통계 화면에 뜨는 모든 숫자는 받아 놓은 레코드에서 뽑아낸 값입니다.
SwiftUI는 화면을 다시 그릴 때마다 `body`를 다시 실행하므로, 그 안에서 집계하면 **행마다 · 프레임마다**
전체 레코드를 다시 훑게 됩니다(프로젝트 N개면 O(N × 레코드 수)). 그래서 집계 결과는
`FeedbackStore.Derived`에 한 번 만들어 두고, **입력이 바뀔 때만** 버립니다.

- 캐시되는 것: 프로젝트별 트래픽·요약·설치 분포, 진단 롤업, 이벤트 집계·내역, 지표 평균·플래그,
  추이 차트, 그리고 프로젝트별로 나눠 놓은 레코드 묶음
- 캐시되지 않는 것: 검색어·정렬·필터가 걸린 목록(`filteredFeedback`) — 입력이 매번 달라집니다
- 무효화는 **바뀐 것만** 버립니다. 전부 버리면 읽음 표시 하나에도 전체 레코드를 다시 훑게 됩니다.
  - 받아 온 레코드·숨긴 프로젝트 → 전부 (`invalidateDerived()`)
  - 읽음·확인 표시 → 프로젝트 카드의 안 읽음 수만 (`invalidateReadState()`)
  - 학습된 앱 이름 → 이름을 보여주거나 이름으로 정렬하는 것만 (`invalidateLabels()`)
  - 새 이벤트 합산 → 사용량 관련만 (`invalidateUsageRollups()`)
- 자동 갱신이 **아무것도 못 찾았으면 아무것도 대입하지 않습니다**. 같은 값이라도 대입하면
  `didSet`이 돌아 집계를 통째로 버리므로, 1분마다 헛되이 다시 계산하게 됩니다.

대신 "최근 7일" 같은 창은 **계산한 시점에 고정**되고 시계를 따라 미끄러지지 않습니다. 다음 새로고침
(자동 갱신 주기, 최소한 실행할 때마다)에 갱신되므로 하루 단위 버킷보다 훨씬 촘촘합니다.

## 5-2. 이벤트는 도착할 때 한 번만 집계합니다 (일 단위 롤업)

`UsageEvent`는 끝없이 늘어나는 유일한 레코드 타입입니다. 전부 들고 있다가 화면마다 다시 합치면
쓸수록 느려지는데, 이건 방향이 반대입니다. 그래서 이벤트는 **처음 읽은 그 순간 자기 날짜에 더해지고**,
그 뒤로는 날짜만 남습니다(`UsageRollups`).

```
프로젝트 → "2026-08-28" → { 건수, 그날 활동한 installID 집합, 이벤트명별 건수 }
```

- 주·월·연은 일 버킷의 **합**이고, 활동 사용자는 일별 installID 집합의 **합집합**입니다
  (월·화에 모두 쓴 설치는 두 명이 아니라 한 명).
- 합산은 **몇 번 해도 같습니다**. 각 날짜가 이미 센 레코드명을 들고 있어서, 겹치는 증분 조회나
  전체 재조회가 같은 이벤트를 다시 줘도 숫자가 부풀지 않습니다.
- 그 레코드명 집합만 180일 뒤에 정리됩니다(`idRetentionDays`). 그 뒤로 그 날은 "닫힌" 상태가 되어
  뒤늦게 온 이벤트를 세지 않습니다 — **건수는 영구히 남습니다**.
- 레코드 원본은 최근 90일치만 남습니다(`rawEventRetentionDays`). 개별 이벤트를 한 줄씩 보여주는
  **사용 내역** 카드만 원본이 필요하고, 나머지 숫자는 전부 롤업에서 나옵니다.

결과적으로 비용이 **이벤트 수가 아니라 하루 수**에 비례합니다. 새로 도착한 것만 합산하고, 이미 합산한
것은 다시 보지 않습니다.

## 5-3. 성장 상한(carrying capacity)은 이렇게 잽니다

신규가 늘어도 이탈률이 그대로면 활동 사용자는 어느 선에서 멈춥니다. 그 선이 성장 상한입니다.

```
다음 기간 활동 = 이번 기간 활동 × (1 − 이탈률) + 기간당 신규
              ⇒  상한 = 기간당 신규 ÷ 기간 이탈률
```

- **활동 사용자** = 그 기간에 이벤트를 보낸 서로 다른 설치. 일 버킷(§5-2)의 installID 집합을
  주/월로 **합집합**한 값입니다. 스냅샷(`UsageSnapshot`)은 설치마다 한 줄을 덮어쓰기 때문에
  "지난달에 활동했는가"를 되돌아볼 수 없고, 이탈은 정의상 과거와의 비교라 롤업 위에서 잽니다.
- **신규** = 이 허브에서 **처음 활동한** 설치. 스토어 다운로드가 아니고, 스냅샷 기준 `new7`과도
  다른 숫자입니다. 이탈률과 같은 모집단에서 나와야 둘의 나눗셈이 뜻을 갖기 때문입니다.
- **이탈** = 지난 기간에 활동했는데 이번 기간에 아무 이벤트도 보내지 않은 설치.
  이탈률은 창 전체의 `이탈 합 ÷ 직전 활동 합`입니다 — 기간별 비율을 다시 평균 내면 활동이
  3명이던 주가 300명이던 주와 같은 무게를 갖습니다.
- **창**: 주간은 최근 8주, 월간은 최근 6달. **진행 중인 기간**(아직 안 끝난 이번 주/달)과
  **기록의 첫 기간**은 뺍니다. 앞은 숫자가 덜 찼고, 뒤는 그때 모두가 "처음 활동"이라 신규가
  유입이 아니라 그동안 쌓인 전부이기 때문입니다.
- **활동이 없던 기간도 한 칸을 차지합니다.** 건너뛰면 수집이 멈춘 구간이 조용히 사라지고
  이탈이 없었던 것처럼 보입니다. 대신 그런 기간이 섞이면 화면에 경고로 적습니다.
- 이탈이 한 번도 관측되지 않으면 상한은 무한대이므로 **숫자를 내지 않습니다**(`—`).
  표본이 모자라거나(주 4회·월 3회 미만), 활동 사용자가 한 자릿수이거나, 신규가 0이면
  그 사실을 카드 안에 그대로 적습니다 — 숨기면 잘못 믿게 됩니다.
- 앱이 **주요 행동만** 이벤트로 보내므로, 열어만 보고 아무것도 하지 않은 설치는 활동에
  들어오지 않습니다. 상한은 "이 앱을 실제로 쓰는 사람 수"의 상한입니다.

계산은 다른 통계와 같이 새로고침마다 한 번만 하고 캐시합니다(§5-1).

## 5-4. 심볼로 되돌리기 (오프셋 → 함수 이름)

콜스택의 `+820588` 은 함수 이름이 아니라 **텍스트 세그먼트 기준 오프셋**입니다.
이름까지 보려면 **정확히 그 빌드의 dSYM** 이 있어야 합니다. 버전 이름만으로는 못 고릅니다
(같은 5.0.6 이라도 빌드가 여럿입니다). 그래서 앱이 스택 끝에 바이너리마다 UUID 를 실어 줍니다.

```
 0 ClipKeyboard +820588
 1 SwiftUI +1042364
...
--
@ ClipKeyboard 794FD256-8A8D-3C8D-91AA-AAC27EF3512C
```

### 준비 (한 번)

**dSYM 을 버리지 않는 것**이 전부입니다. 아카이브 안에 들어 있지만, 아카이브를 지우면 같이 사라집니다.

- Xcode: Organizer → Archives → 해당 아카이브 우클릭 → **Show in Finder** →
  패키지 내용 보기 → `dSYMs/` 폴더. 이걸 따로 보관합니다.
- Xcode Cloud / App Store Connect 로 올렸다면 Organizer 에서
  **Download Debug Symbols** 로 내려받습니다.
- Spotlight 가 색인하는 자리에 두면 아래 `mdfind` 가 UUID 로 바로 찾아 줍니다.

### 되돌리기

이슈 상세의 콜스택 아래 **"심볼 복원 명령 복사"** 버튼이 아래 두 줄을 만들어 줍니다.

```bash
# ① UUID 로 그 빌드의 dSYM 찾기
mdfind "com_apple_xcode_dsym_uuids == 794FD256-8A8D-3C8D-91AA-AAC27EF3512C"

# ② 오프셋을 함수 이름으로
atos -o <위에서 찾은 경로>/Contents/Resources/DWARF/ClipKeyboard \
     -arch arm64e -l 0x100000000 0x1000c856c
```

`-l 0x100000000` 은 64비트 앱의 텍스트 세그먼트 시작이고, 마지막 주소는 `시작 + 오프셋` 입니다.
`mdfind` 가 아무것도 못 찾으면 그 빌드의 dSYM 이 이 기기에 없다는 뜻입니다.

`-arch` 는 기기에 맞춥니다. 요즘 아이폰은 `arm64e`, 그 이전은 `arm64` 입니다
(`deviceType` 이 iPhone11,x 이상이면 `arm64e`).

### 안 되는 것

- **애플 프레임워크 프레임**(UIKitCore·SwiftUI 등)은 되돌릴 수 없습니다. 그쪽 dSYM 이 없습니다.
  그래서 이슈 화면은 **내 코드 프레임을 굵게** 그립니다. 볼 곳이 거기입니다.
- 옛 형식 레코드는 오프셋 자체가 안 실려 있어 되돌릴 것이 없습니다.

FeedbackHubViewer/
